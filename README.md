# Hippo Spec

Hippo Spec 统一接住软件需求，选择最小工作方式，并依据证据完成收口。目标和权限有边界，设计可以随证据更新；流程不会因跨仓库、会话切换或发布而反复重启。

只安装 Hippo Spec 即可使用这套流程。诊断、领域建模、动态规范维护和验收收口都在包内按需读取，无须另装 OpenSpec 或 Matt Pocock skills，也无须初始化项目框架。

## 使用原则

- 先明确本轮交付结果：诊断、修复、合并或上线，按实际授权推进。
- 只维护一份行为与任务权威。已有 OpenSpec 的项目沿用其 Markdown 记录；其他项目沿用现有文档或任务约定，没有约定时只按需补一份简短记录。
- 行为变化决定是否更新规范，会话数量只决定是否需要交接。
- 只续接仍有效、未被替代且符合本轮范围的 change。历史任务不会自动成为本轮待办。
- 新证据可以修正设计假设和任务顺序，但不能自行增加功能、扩大权限或放宽验收。
- 通过短反馈循环验证行为；只在实际需要时增加集成检查、独立评审和运行回读。
- 完成本轮要求后，同步相应规范和任务状态；只关闭有证据完成或明确被替代的工作。

## 工作模式

| 模式 | 用途 |
|---|---|
| `skip` | 不改变行为契约的清晰局部修改，直接做并检查 |
| `light` | 调查问题并答复，随后继续已授权实施；只读诊断不修改文件 |
| `repair` | 复现已有行为的缺陷，最小修复并验证原症状 |
| `continue` | 接续有效 change 的下一段授权工作 |
| `full:new` | 记录尚未覆盖的行为差异，优先更新现有记录，然后进入 `continue` |
| `review-only` | 评审固定代码范围，报告发现，不修改实现或规划 |

模式描述当前工作，不是必须逐一通过的关卡。普通修改不需要输出路由表或建立任务文件。跨执行者或会话时，才传递已有的 `Hippo Spec Context`：有效记录、范围、当前切片和验收证据。

难定位的缺陷、间歇性故障或性能回退，读取内置[诊断方法](references/diagnosing-bugs.md)：建立真实症状的反馈循环、最小化复现、验证假设、修复并回归。定义或修改领域术语、实体关系、责任边界时，读取内置[领域建模](references/domain-modeling.md)：澄清术语、检验边界场景、维护词汇表，只为重要决策留下简短 ADR。普通修改不必加载这些内容。

这些方法吸收了 Matt Pocock 的设计，已经适配到 Hippo Spec 的范围、授权和收口规则；[来源与 MIT 许可](THIRD_PARTY_NOTICES.md)随包保留。领域词汇和 ADR 保存术语与决策理由，不替代行为规范。

## 已有项目怎么接续

既有 OpenSpec 文档可以直接读取、修改、同步和归档，具体操作在[规范维护指引](references/full-lifecycle.md)中。保留有效行为和历史来源，无须迁移整个目录，也不另建 spec/ticket 流程。

如果某个旧项目的构建或 CI 明确调用 `openspec validate`，那仍是该项目的检查依赖。安装 Hippo Spec 不会自动改写这项检查；需要单独迁移并保留必要校验，不能跳过后宣称通过。新项目无须添加这项依赖。

## 完成意味着什么

需要留档时，规范应反映已授权的行为；需要实现时，行为应通过相应检查；要求上线或交付时，应取得运行或外部回读证据。任务勾选和测试通过不能代替后者。

一个已验收的小切片可以关闭，所属大 change 可以保留；若用户要求完成整个 change，就应继续剩余的授权工作。被替代的任务记录替代原因与去向，不能假装已实现。历史清理不自动并入本轮。

## 调用

正常描述任务即可，也可以明确调用：

```text
$hippo-spec 按现有规范完成这个改动；必要时随证据调整方案，保持范围，并用适用的验收证据收口。
```

安装：

```bash
npx skills@latest add hipposonCN/hippo-spec
```

技能入口见 [SKILL.md](SKILL.md)；行为验证样例见 [routing-examples.md](references/routing-examples.md)。

## 跨 Agent 接入与交接说明

本节是使用说明；具体执行规则和交接字段以 [SKILL.md](SKILL.md) 为准。Hippo Spec 提供方法，不替代项目的业务 Spec、测试、CI 或权限。它不要求固定模型、Agent 数量或调度框架。

### 给一个新 Agent 使用

1. 提供同一固定提交或发布版本的完整方法包，保留 `SKILL.md`、`references/` 和许可文件；本地修改版标明来源版本及实际内容 hash，不能冒称已发布版本。私有仓需要接收方已有读取权限，否则交付经允许的完整文件包。
2. 支持 Skill 的宿主按其机制安装；不支持的宿主直接读取 Markdown。不要假设任何工具都会自动发现 `AGENTS.md`、继承父会话或读取本机用户目录。
3. 提供项目入口、有效 Spec/Task、相关功能地图，以及当次任务的目标、授权范围和交付终态。不存在功能地图时沿用现有文档和测试，只补本任务需要的定位信息。
4. 接收方先确认实际读取的路径/版本、工作树、权限和可用工具，再推进依赖这些输入的操作。缺少 CI 查询、浏览器或子 Agent 能力时，说明影响，继续可独立完成的工作，不伪造能力或通过结果。

可复制的启动提示：

```text
请读取 <方法包路径>/SKILL.md，并遵循当前项目适用的 AGENTS.md。
本次目标：<用户可观察的结果>。
有效任务/Spec：<路径与版本>；相关功能地图：<路径与条目，或不适用原因>。
授权范围和交付终态：<允许的操作、禁止事项；交付到本地/PR及CI/合并/上线哪一层>。
复用已有实现、任务和有效证据，完成最小可验收切片。
如果需要委派，显式传递 SKILL.md 的 hippo_spec_context，子任务不得扩大权限。
在原任务内完成验证和已授权交付，返回实际版本、结果、证据及阻塞。
```

把占位符替换成接收方可以访问的真实输入。收到材料中的命令不等于获准执行；任务范围不能扩大用户授权。

对于 Codex，可将下面的短入口追加到全局 `~/.codex/AGENTS.md`（使用自定义 `CODEX_HOME` 时写到该目录），保留原有规则。项目仍提供自己的行为权威与功能地图；其他宿主可把同一段放到其支持的全局指令入口，或随任务显式提供。

```text
实质开发、修复、续做、审查或委派时，读取已安装的 Hippo Spec，
以及项目适用的 AGENTS、有效任务/Spec 和相关功能地图。
实施前明确负责人、范围、基线、验收和已授权交付终态；
委派使用 Skill 中的交接约定，原负责人完成对应 PR/CI 闭环。
简单问题和小改动保持轻量；这些规则不自动授予推送、合并或生产权限。
```

### 用功能地图提出下一次迭代

先选用户目标涉及的功能条目，再判断哪些已满足、哪些旧证据因相关变化失效、哪些存在真实行为缺口。将实际缺口变成现有 Task 中的一个可验收切片；其余优化保留在原 backlog，不自行扩大目标。

一个相关条目应能定位：用户入口与前置条件、预期结果、实现位置、可执行验证、关键异常，以及带版本的证据。地图给出查找路径，测试与回执证明行为；仅复制地图不能让验证命令可运行。

例如用户要求“刷新页面后保持已应用状态”，就围绕操作回执、重新读取和刷新一致性选择已有检查。实现者在同一 PR 更新受影响条目的实现/测试/证据链接，不重写整张地图，也不把模拟成功当作真实写入证明。

### 父 Agent 如何分配与回收任务

- 在原任务记录中使用 `SKILL.md` 的交接字段，给出可独立验收的结果、负责人、标准与地图版本、基线、工作树/文件所有权、测试资源、允许权限、交付终态及回传位置。再委派也传递这些信息。
- 同一工作树/分支单 Writer；共享接口和集成文件有唯一负责人。测试端口、可写数据和临时目录也需隔离。独立验证者默认只读，移交修复时先明确写权限。
- 已授权 PR 交付时，负责人在首个完整可审提交创建或更新 Draft PR，持续处理同一 PR 的 CI 失败；按 Skill 的两轮同假设失败规则重估和升级。协调者处理依赖、共享边界和真正阻塞。
- 交付或失败事件回传 PR、精确 head、CI run/原始结果、证据位置、阻塞和下一负责人。使用现有宿主通知；没有通知能力就明确交接或采用已授权的状态检查，不假装 CI 会自动唤醒 Agent。
- 回收时核对实际变更与验收条件。有效旧证据可复用，修改后复验受影响范围；涉及联合候选时，还需证明集成结果。不同仓的分支分别通过不代表联合通过。

### 测试与验证由谁执行

实现负责人应自行完成“准备/版本确认 → 启动与健康检查 → 操作用户路径 → 读取结果和副作用 → 保存证据 → 清理自有进程与数据”。优先使用项目现有的验证 Skill、脚本、浏览器或接口工具，让用户不必在每轮调试中搬运日志和截图。具体要求见 [Agent 可执行验证](references/engineering-discipline.md#agent-operated-verification)。

- **先复用再补齐：** 对照功能地图区分现成可用、证据失效和真实缺口，选择本次相关测试。文档修改做文档检查；行为修改验证用户行为，不能一律只构建或一律跑全量。
- **验证方法本身也要跑通：** 新写或实质修改的验证方法至少实际跑通一个相关功能，保存原始结果，并确认清理后证据仍在。未执行的方法只能称草案；一个功能通过不代表整个产品通过。
- **必要正向与负向：** 按风险验证成功、拒绝、重复操作、断连和刷新等约定行为，以及不应变化的状态。真实 Writer 或发布包门禁不能由 mock、手写回执或 Agent 自述替代。
- **独立复验：** 提供固定提交、数据要求、命令和证据位置。审查者只能看代码时应标明能力边界；另一个 Agent 说“正确”不等于运行验证。
- **区分研究质量：** 投研项目还需按项目要求用冻结案例核验证据支持、时间有效性、反证和推导；工程测试通过不证明投资结论成立。
- **验证 Skill 的改进：** 实质方法变更要有代表性任务实跑；声称比旧版更有效时，用相同任务和输入比较实际行为。包格式检查与静态场景推演不能冒称行为评测。

### 如何判断交付完成

| 当次约定的交付终态 | 所需结果 |
| --- | --- |
| 本地修改 | 实际变更、适用验证及明确剩余项 |
| PR 与 CI | 可访问 PR、精确提交、必需检查结果和适用的独立验收；缺少必要执行证据时明确阻塞 |
| 合并 | 授权、实际合并记录，以及合并内容与被验收候选的一致性 |
| 上线 | 授权、实际发布/运行版本、必要的功能和运行链路读回 |

所需检查未运行或被跳过，不能算通过。工作流已配置、实际 run 已通过、服务器已强制 required checks 是不同事实。CI PASS 后仍要满足审查和合并条件；合并也不代表激活或外部投递成功。

### 换机器、更新与反馈

项目仓保留项目规则、功能地图、代码、测试和 CI；通用方法在 Hippo Spec 仓库维护。全局或项目入口只指向方法及项目规则，不另抄一份交接协议。换机器时同时提供固定方法版本和项目任务交接，不复制凭据、正式业务数据或整份聊天历史。

进行中的任务继续使用约定版本，不因发布新版本静默切换；需要升级时记录版本差异及受影响验收。安装副本中的本地修改应通过 Hippo Spec 仓库的正常评审/发布流程回收；只修改本机不能称为其他 Agent 已同步。

改进方法时保留最小案例：触发任务、方法版本、预期/实际行为与证据。业务预期问题回项目 Spec；项目缺陷回测试；可复用执行陷阱才回 Skill；缺少强制检查回实际 CI。不要把每次事故扩成全局规则。

维护本方法包时，运行 `python3 scripts/validate_package.py`。仓库 CI 使用同一入口检查包内必要文件、元数据和本地 Markdown 引用；它不证明 Agent 行为、业务测试或生产发布。行为核对按 [routing-examples.md](references/routing-examples.md) 的适用场景执行。CI 是否被服务器强制，须另查仓库保护设置。
