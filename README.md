# Hippo Spec

**让 Agent 接住一个明确的任务，自己执行、验证，并交付可复核的结果。**

记住一条主线：**规则 → 任务 → 执行与验证 → PR / CI → 授权后的合并或上线**。CI 失败回到原负责人修复；通过后仍要满足对应交付终态的验收和授权。

Hippo Spec 是可跨 Agent 使用的方法包。它把任务范围、现有 Spec、功能地图、真实测试、交接和交付联结起来，让你少解释、少搬运日志和截图。它不依赖固定模型、Agent 数量、OpenSpec CLI 或新的调度框架。

## 先记住这三件事

1. **规则放这里，产品事实留在项目。** Hippo Spec 管方法；项目的 AGENTS、Spec/Task、功能地图、代码、测试和 CI 各自保留原位置，只有一份有效的行为与任务权威。
2. **写了要求，不等于工具已跑通。** 验证方法必须实际操作相关功能并留下证据；包检查不证明产品行为，测试通过不证明研究结论，合并不证明上线。
3. **负责人做到约定终点。** 本地修改、PR 与 CI、合并、生产激活是不同目标。委派不扩大权限；普通修复沿用原负责人和原 PR，协调者主要处理依赖、共享边界和真正阻塞。

## 我想做什么，应该读哪里

| 需要 | 入口 | 交付结果 |
| --- | --- | --- |
| 开发、修复、续做、审查 | [SKILL.md](SKILL.md) | 最小可验收改动，以及当次已授权交付 |
| Agent 不知道从哪里进入、如何验收功能 | [项目验证入口与维护](references/project-verification.md) | 复用现有地图/脚本，补齐真实命令、操作和证据路径；至少一个受影响路径实跑 |
| 把任务交给另一个 Agent | [交接字段](SKILL.md#hand-off-the-same-assignment) | 标准与地图版本、任务范围、基线、所有权、验收、终态及回传位置 |
| 在 Codex 中接续线程、处理 PR/CI 失败 | [Codex 交付操作说明](references/codex-delivery.md) | 按实际工具回到原负责人，核对当前 head、失败日志、修复与检查 |
| 决定需要哪些测试 | [工程验证要求](references/engineering-discipline.md#agent-operated-verification) | 根据 UI、CLI/API、持久写入、性能或集成风险取得适用证据 |
| 判断修改 Skill 后是否更可靠 | [方法行为评测](references/method-evaluation.md) | 固定任务与隔离输入，检查真实动作和产物；不凭 Agent 自述打分 |
| 难定位的 Bug / 领域边界问题 | [诊断](references/diagnosing-bugs.md) / [领域建模](references/domain-modeling.md) | 最小复现、检验假设，或明确术语与责任边界 |
| 接续已有 OpenSpec 或其他规范记录 | [规范维护](references/full-lifecycle.md) | 更新有效记录，不重新初始化流程或清扫无关历史任务 |

这些入口按需读取，不是每个任务都要走一遍的清单。普通文案修改不创建任务体系、验证 Skill 或 Agent 团队。

## 怎么使用

正常描述任务即可；也可以明确调用：

```text
$hippo-spec 按现有规范完成这个改动，复用已有功能地图和测试，
保持范围，并交付到已授权的终态。返回实际版本、结果、证据和阻塞。
```

给新 Agent 或其他工具时，传递同一固定版本的完整方法包，再填入这个任务提示：

```text
请读取 <方法包路径>/SKILL.md 和项目适用的 AGENTS.md。
目标：<用户能观察到的结果>。
有效任务/Spec：<路径和版本>。
相关功能地图：<条目与路径，或不适用原因>。
工作树/基线/所有权：<负责人、SHA、允许文件、隔离测试数据和端口>。
授权范围与终态：<本地 / PR及CI / 合并 / 上线；允许和禁止操作>。
验收与回传：<必要检查、已有有效证据、原线程或任务位置>。
复用有效成果，完成当前范围；委派时传递 hippo_spec_context，子任务只能收窄权限。
```

占位符必须替换成接收方可访问的输入。不要依赖聊天历史自动继承，也不要把绝对本机路径当成跨机器地址。私有仓库需要接收方自己的读取权限；不传递凭据或正式业务数据。

## 功能地图如何推动迭代

先定位目标涉及的条目，再区分：**已具备且证据有效、证据被相关变化作废、真正缺失**。只把当前目标的缺口接入原 Task，其余优化留在现有 backlog。

一个有效条目能定位用户入口、前置条件、实现、操作方法、成功和关键异常、带版本的证据。实现者在同一交付中更新受影响条目，不另画一套地图。维护时区分文档漂移、验证工具缺口和产品回归，不能通过修改地图掩盖 Bug。

## 多 Agent 如何配合

一个 worktree/分支只有一个 Writer；共享接口与集成文件指定唯一负责人；端口和可写测试数据隔离。独立审查者默认只读。负责人自主完成实现、适用测试、提交及已授权 PR/CI 修复，修复返回同一任务。

协调按交付、失败和阻塞事件推进。相同提交与相关输入下的有效证据直接复用；无变化不重复全量审查。联合候选仍需验证实际组合，不能用各分支分别通过代替。

**持续执行的三个状态要分别记录：**当前回合正在等待、已配置定时接续、事件确实唤醒原负责人。一个等待 API 或一段“持续修复”的文字不能证明后台自动接续。缺少能力时明确交接，不自动搭建轮询服务。

## 验证什么才算完成

| 层级 | 需要的证据 |
| --- | --- |
| 方法包完整 | 文件、元数据、本地引用检查通过 |
| 方法能被执行 | 新建/实质修改的验证方法在隔离环境实跑，原始结果与清理后证据可读 |
| 产品行为正确 | 从真实相关用户入口操作，核对结果、副作用和必要异常；mock 只证明其声明边界 |
| PR 与 CI | 当前精确 head 的实际检查结果及必要审查；配置了工作流不等于 run 通过或 required checks 强制 |
| 合并或上线 | 对应授权、实际合并/运行版本，以及所需的功能和链路读回 |
| 研究质量 | 按项目冻结案例检查证据支持、时间有效性、反证和推导；工程通过不能代替 |

必要检查未运行或被跳过时，该层阻塞。保存原始失败，不降低断言换绿色。同一假设下两轮实质修复仍失败，重新检查假设、输入与环境，再带反证升级。

## 固定案例怎么运行

仓库提供四个本地案例：`small-edit`、`required-check`、`ci-repair`、`release-boundary`。准备一个不存在的隔离目录：

```bash
python3 scripts/prepare_method_case.py ci-repair --output /tmp/hippo-cli
```

把生成的 `request.txt`、`workspace/` 和固定方法版本交给新 Agent；协调者保留 `assessment.json`，检查实际命令、差异和结果。详细操作和清理见[行为评测方法](references/method-evaluation.md)。

**生成器和它的单元测试不会调用模型。**本地修复案例不等于真实 GitHub CI 失败接续；一次方法包案例不等于 Research OS / Claim Apply 验收。实际执行了哪些案例、哪些接续方式已验证，以对应 PR/Release 证据为准。没有受控前后比较时，不宣称提效比例或可靠性提升。

维护本包的确定性检查：

```bash
python3 scripts/validate_package.py
python3 -m unittest discover -s tests -v
```

它们检查包与案例工具，不替代 Agent 行为评测。原有[决策场景](references/routing-examples.md)用于补充边界核对，不要求每次全跑。

## Skill 还是 Plugin？

**当前继续以一个完整 Skill 包分发，不需要先转 Plugin。**安装后即可使用方法；Plugin 主要解决发现、安装和分发，不会自动获得项目测试、CI 强制或后台唤醒能力。

当需要一起分发多个独立 Skill、连接器，或通过插件市场统一安装时，再在同一仓库增加薄包装，复用同一份源文件和版本。不要复制两套规则，也不要同时安装同名 Skill 与 Plugin 造成重复发现。当前发布不包含 Plugin 清单或市场安装承诺。

支持 Skill 的宿主按其安装机制读取本仓根目录；其他 Agent 直接读取 Markdown。现有安装方式也可使用：

```bash
npx skills@latest add hipposonCN/hippo-spec
```

安装与转移时保留完整包，包括 `references/`、`scripts/`、`tests/`、`agents/` 和许可。需要固定版本时使用对应 Git tag/commit，检查安装后的文件是否完整；不假定各安装工具都有相同的版本参数。

## 全局入口与更新

Codex 可在现有全局 `~/.codex/AGENTS.md`（自定义 Codex home 则用其路径）保留短入口，项目规则仍由项目提供：

```text
实质开发、修复、续做、审查或委派时，读取已安装 Hippo Spec，
以及项目适用的 AGENTS、有效任务/Spec 和相关功能地图。
明确范围、负责人、基线、验收和已授权交付终态；原负责人完成对应闭环。
简单修改保持轻量；这些规则不授予推送、合并或生产权限。
```

不同宿主的发现目录、线程 API 和权限不同，按实际能力适配。已运行任务不因方法发布而静默更换约定版本。本地副本的改进通过本仓 PR/Release 回收，更新后核对固定版本；只改一台机器不能声称所有 Agent 已同步。
